## 6. Targeted Pseudocode

Three flows qualify under the criteria (algorithmic complexity + concurrency-sensitivity + multi-step writes with rollback). Other flows (e.g., `record_answer`, `record_assessment`) are simple enough that pseudocode would just duplicate `/plan`'s task breakdown.

### 6.1 Flow: `start_session(book_id, scope, theme)`

Entry: `POST /api/v1/books/{book_id}/quiz-sessions`

```
FUNCTION start_session(book_id, scope, theme):
  # Validate input
  IF scope.mode NOT IN {'all_summaries', 'specific_chapters'}: raise 400
  IF scope.mode == 'specific_chapters':
    IF NOT scope.section_ids: raise 400 ("Pick at least one chapter")
    IF NOT all_belong_to_book(scope.section_ids, book_id): raise 400
    token_count = sum(tiktoken_count(section.content_md) for section in sections)
    IF token_count > settings.quiz.specific_chapters_token_budget: raise 400 (budget)
  IF scope.mode == 'all_summaries':
    IF book.default_summary IS NULL AND no section summaries: raise 400 ("Generate summaries first")
  IF llm_provider IS NULL: raise 503

  # Create session row inside a transaction (G10 atomicity also applies here)
  BEGIN TRANSACTION
    session = INSERT quiz_sessions(book_id, scope, theme, status='in_progress')

    # D29 warm-up phase (FR-21)
    warm_up_candidates = compute_warm_up_candidates(book_id, scope)  # see §6.2
    warm_up_count = 0
    FOR candidate IN warm_up_candidates[:settings.quiz.warm_up_max_questions]:
      try:
        question = generate_question(
          session_id=session.id, book_id, scope, theme=None,
          warm_up=True, concept_label_hint=candidate.concept_label,
        )
        INSERT quiz_questions(...question..., warm_up=True)
        warm_up_count += 1
      except LLMError:
        # Don't block session start — fall through to cold-start Q1
        log("warm-up generation failed; continuing", concept=candidate.concept_label)

    IF warm_up_count > 0:
      first_question = first_warm_up_question
      queue_hit = False
    ELSE:
      # Pre-drafted Q1 eligibility (FR-22, S3, E14, E19, G14 fix)
      eligible = (
        scope.mode == 'all_summaries'
        AND theme IS NULL
        AND book.pre_drafted_q1_id IS NOT NULL
        AND quiz_questions[book.pre_drafted_q1_id].is_stale == False
      )
      IF eligible:
        first_question = quiz_questions[book.pre_drafted_q1_id]
        UPDATE quiz_questions SET session_id = session.id, is_pregen = False WHERE id = first_question.id
        UPDATE books SET pre_drafted_q1_id = NULL WHERE id = book_id
        queue_hit = True
      ELSE:
        first_question = generate_question(session.id, book_id, scope, theme, warm_up=False)
        INSERT quiz_questions(...first_question..., warm_up=False)
        queue_hit = False
  COMMIT

  RETURN {session, first_question, warm_up_count, queue_hit}
```

**DB calls:**
- `INSERT quiz_sessions` (1)
- `SELECT FROM quiz_questions WHERE book_id=? AND ...` for warm-up candidates (1, see §6.2)
- `INSERT quiz_questions` × warm_up_count + 1 (Q1)
- `SELECT books WHERE id=?` for pregen eligibility (1)
- `UPDATE quiz_questions SET session_id=?, is_pregen=False WHERE id=?` (0 or 1)
- `UPDATE books SET pre_drafted_q1_id=NULL WHERE id=?` (0 or 1)

**State transitions:**
- new session: `(none) → in_progress`
- pregen Q1: `is_pregen=True, session_id=NULL → is_pregen=False, session_id=<new>`

**Error branches:**
- 400 invalid scope / budget / no summaries — pre-transaction
- 503 LLMProvider is None — pre-transaction
- LLM failure during warm-up generation — caught and logged; session start proceeds with cold-start Q1 (gracefully degrades from "warm-up + Q1" to "Q1 only")
- LLM failure during cold-start Q1 — propagates as 502; transaction rolls back → no orphan session
- 504 LLM subprocess timeout (G13) — same as 502 path
- DB busy on COMMIT — retry once at API layer; if fails, 500 to caller

**Concurrency notes:**
- Two concurrent start_session calls for the same book on different devices: both succeed, two `in_progress` sessions exist. FR-19 (G28 patch) catches this on next tab mount via the resume/abandon banner.
- Pregen-slot consume race: if two concurrent eligible sessions race, both will try to UPDATE `books SET pre_drafted_q1_id=NULL WHERE id=?`. SQLite's row-level lock means one wins; the other reads the new state. The "loser" path falls through to cold-start. Acceptable — we do NOT add a CAS column; the second session just gets fresh generation, which is correct.

### 6.2 Flow: `compute_warm_up_candidates(book_id, scope)`

Entry: called from `start_session`.

```
FUNCTION compute_warm_up_candidates(book_id, scope):
  # FR-70: last 3 completed sessions for this book
  recent_sessions = SELECT * FROM quiz_sessions
    WHERE book_id=? AND status='completed'
    ORDER BY ended_at DESC LIMIT settings.quiz.warm_up_lookback_sessions   # default 3

  IF len(recent_sessions) == 0: RETURN []

  # FR-70(b): collect concept_labels with user-Missed/Partial OR agent-incorrect/partial
  candidate_labels = SELECT DISTINCT concept_label, citation_json FROM quiz_questions
    WHERE session_id IN recent_session_ids
      AND is_stale = 0
      AND (
        self_assessment IN ('partial', 'missed')
        OR agent_verdict IN ('partial', 'incorrect')
      )

  # FR-70(c): exclude any concept_label later marked 'got_it' in any subsequent session
  # Subsequent = session.created_at > the candidate-yielding session's created_at
  resolved_labels = SELECT DISTINCT concept_label FROM quiz_questions q
    JOIN quiz_sessions s ON q.session_id = s.id
    WHERE q.book_id = ?
      AND q.is_stale = 0
      AND q.self_assessment = 'got_it'
      AND s.created_at > min(candidate_session.created_at)

  unresolved = candidate_labels - resolved_labels

  # FR-70(d): scope filter
  IF scope.mode == 'specific_chapters':
    unresolved = [c for c in unresolved if c.citation.section_id IN scope.section_ids]

  # Order by recency of the candidate-yielding question
  RETURN sort by created_at DESC, take settings.quiz.warm_up_max_questions  # default 2
```

**DB calls:**
- `SELECT quiz_sessions LIMIT 3` (1)
- `SELECT DISTINCT concept_label, citation_json` candidate query (1)
- `SELECT DISTINCT concept_label` resolved-labels query (1)
- 3 total reads, all O(N) where N = recent question count.

**State transitions:** N/A — pure read query.

**Error branches:** None (gracefully returns []).

**Concurrency notes:** None — pure read; the result is consumed immediately by `start_session` inside the transaction. If a parallel session is being committed during read, the candidate set may be slightly stale; impact is at most one missed warm-up — recoverable on next session.

**G16 concept_label drift dependency:** the JOIN `WHERE concept_label = ?` (implicit in `candidate_labels - resolved_labels` set difference) is exact-match. The G16 normalization patch (strip parentheticals, collapse hyphens/whitespace) is a HARD prerequisite for this flow to work correctly across sessions — without it, the set difference silently misses concept variants.

### 6.3 Flow: `stop_session(session_id)`

Entry: `POST /api/v1/quiz-sessions/{sid}/stop`

```
FUNCTION stop_session(session_id):
  BEGIN TRANSACTION  # G10 atomicity
    session = SELECT * FROM quiz_sessions WHERE id=? FOR UPDATE
    IF session IS NULL: raise 404
    IF session.status IN {'completed', 'abandoned'}:
      # G10 idempotency: re-stop is a noop, return current state
      COMMIT
      RETURN session

    # Determine final status (FR-25)
    answered_count = SELECT count(*) FROM quiz_questions
      WHERE session_id=? AND user_answer IS NOT NULL AND discarded=0
    final_status = 'completed' IF answered_count > 0 ELSE 'abandoned'

    UPDATE quiz_sessions
      SET status=final_status, ended_at=now(), updated_at=now()
      WHERE id=?

    # G1+G7: enqueue rollup gate
    IF final_status == 'completed':
      INSERT processing_jobs(step='QUIZ_ROLLUP', book_id=session.book_id, status='PENDING')
    # else: abandoned — no rollup enqueue
  COMMIT  # if INSERT fails (integrity / DB busy), entire transaction rolls back → 500 to caller

  RETURN session
```

Worker handler for QUIZ_ROLLUP (separate process):
```
FUNCTION handle_quiz_rollup(job):
  book_id = job.book_id
  state = SELECT * FROM quiz_dedup_state WHERE book_id=?  # may be NULL — first time
  current_count = SELECT count(*) FROM quiz_questions WHERE book_id=? AND is_stale=0 AND ...

  # FR-61 + G18 delta gate
  IF current_count <= settings.quiz.dedup_verbatim_cap: noop_complete; return
  IF state IS NOT NULL AND (current_count - state.last_rollup_question_count) < settings.quiz.rollup_delta_threshold:
    noop_complete; return

  # Compute rollup
  stems = SELECT stem FROM quiz_questions WHERE book_id=? AND is_stale=0 ORDER BY created_at DESC
  themes_summary = llm_provider.generate(rollup_prompt(stems))

  UPSERT quiz_dedup_state(book_id) SET
    themes_summary=themes_summary,
    themes_summary_computed_at=now(),
    last_rollup_question_count=current_count
```

**DB calls:**
- `SELECT quiz_sessions WHERE id=? FOR UPDATE` (1)
- `SELECT count(*) FROM quiz_questions ...` (1)
- `UPDATE quiz_sessions ...` (1)
- `INSERT processing_jobs ...` (0 or 1, gated)

**State transitions:**
- session: `in_progress → completed` (≥1 answered) or `in_progress → abandoned` (0 answered)
- processing_job: `(none) → PENDING` (gated)

**Error branches:**
- 404 session not found
- 200 idempotent re-stop on already-terminal session (no transaction, just read+return)
- 500 on `INSERT processing_jobs` failure → transaction rolls back, caller retries by re-clicking Stop (idempotent per G10)
- 500 on UPDATE conflict (row locked elsewhere) — async transaction retries via SQLAlchemy's standard retry, then surfaces

**Concurrency notes:**
- `FOR UPDATE` ensures no two concurrent stops on the same session race. SQLite WAL + BEGIN IMMEDIATE gives this.
- Two devices clicking Stop: first wins, second reads `status='completed'` and short-circuits to the idempotent return path — no second `INSERT processing_jobs` (would have been duplicated otherwise).
- Worker handler for QUIZ_ROLLUP: separate process; runs after COMMIT. If two rollup jobs for the same book somehow get enqueued (race + non-deduplicated queue), both run — second one reads `last_rollup_question_count` updated by first, hits delta gate, noops. Self-healing.
